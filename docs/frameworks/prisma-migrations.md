# Prisma Migrations

Prisma Migrate is a powerful tool that helps you manage your database schema changes in a structured
and version-controlled manner.
It allows you to create, apply, and track migrations, ensuring that your database schema stays in sync
with your Prisma schema.

## Creating a Migration

To create a new migration in your local environment, use the following command:

```bash
pnpm prisma migrate dev --name <migration_name>
```

This command generates a new migration file based on the changes in your Prisma schema and applies it to the database.

The generated migration files are managed in the repository.

```console
$ tree ./prisma/migrations/
./prisma/migrations/
├── 20261001091840_init
│   └── migration.sql
└── migration_lock.toml
```

There is a similar command called `db push`, but it differs in purpose because it updates the database directly
from the schema file rather than using migration files. I cannot think of a use case for it at the moment.

## When you want to modify the migration SQL yourself

After creating a migration using `pnpm prisma migrate dev`, you can navigate to the generated migration file
in the `prisma/migrations` directory and make any necessary changes to the SQL statements.

Consider the following scenarios:

- Adjusting SQL generated by Prisma
- Creating and modifying database objects (Views, Functions, Triggers, Procedures)
- Custom data types (Enums, Composite Types)
- Specialized indexes (partial indexes, expression-based indexes, GIN, GiST)
- Permissions and constraints
- Database-specific features (sequences, collations, full-text search)
- Dropping an existing table

```bash
pnpm prisma migrate dev --create-only --name <migration_name>
```

Modify the file generated by this command.

Apply the corrected migration:

```bash
pnpm prisma migrate dev
```

This command applies the changes to the database.

## Applying Migrations

This command applies the changes to the production or staging environment database:

```bash
pnpm prisma migrate deploy
```

> [!WARNING]
> Be sure to use this command for application in environments other than the development environment.
> The `dev` command apparently issues a `reset` in some cases, which causes existing data to be lost.

We recommend trying this first when applying repository-managed migrations to your own development environment.

## Rolling Back a Migration

The method for rolling back depends on the situation.

First, please note that table changes in the production environment cannot be rolled back; you must always add
a new migration to revert the changes.

A simple way to reset the development environment is to delete the migration files and perform a reset.

```bash
pnpm prisma migrate reset
```

The migrations will be reapplied from the beginning, so data will be lost.

## Database-First and Baseline Creation

In some cases, you may start with an existing database and want to create a baseline migration for it.
This is often referred to as the "database-first" approach.

This applies when you start using Prisma migrations with an existing database.

Introspect the existing database to generate the Prisma schema:

```bash
pnpm prisma db pull
```

Updates `prisma/schema.prisma`; an error will occur if the file does not exist.

The schema has been created, but as it stands, there are no migration files, so additional migrations cannot be generated.

Create the initial migration from the command line:

```bash
# create directory
mkdir -p prisma/migrations/20261005000000_baseline

pnpm prisma migrate diff \
  --from-empty \
  --to-schema prisma/schema.prisma \
  --script > prisma/migrations/20261005000000_baseline/migration.sql
```

Furthermore, register the fact that the migration has been applied within the database management system:

```bash
pnpm prisma migrate resolve --applied 20261005000000_baseline
```

You are now ready to launch the `prisma migrate dev` command in the development environment

```console
$ pnpm prisma migrate dev

Loaded Prisma config from prisma7.config.ts.

Prisma schema loaded from prisma/schema.prisma.
Datasource "db": PostgreSQL database "prisma", schema "public" at "postgres:5432"

Already in sync, no schema change or pending migration was found.
```

## Squashing migration history

Reading the official explanation reveals another aspect of the baseline:
"squashing an excessive number of migrations and consolidating them into a single baseline."

Reset the contents of your local `./prisma/migrations` folder to match the migration history on the main branch

### Reset Local Migrations and Create a Squashed Migration

Please revert the contents of the `./prisma/migrations` folder to the state they were in at the point
where you want to start the squashing process. In other words, delete the migrations that occur after that point.

```console
prisma/migrations/
├── 20261005000000_baseline
│   └── migration.sql
├── 20261005072036_add_created # ← remove
│   └── migration.sql
├── 20261005072437_add_updated # ← remove
│   └── migration.sql
└── migration_lock.toml
```

Reset database:

```bash
pnpm prisma migrate reset
```

Create a new migration:

```bash
pnpm prisma migrate dev --name squashed_migrations
```

```console
prisma/migrations/
├── 20261005000000_baseline
│   └── migration.sql
├── 20261005091234_squashed_migrations
│   └── migration.sql
└── migration_lock.toml
```

### How to create a new migration without resetting

To do this, you will need a Prisma shadow database.

```ts
// prisma7.config.ts
export default defineConfig({
  datasource: {
    shadowDatabaseUrl: process.env['SHADOW_DATABASE_URL'],
  },
})
```

```ini
# .env
SHADOW_DATABASE_URL="postgresql://{user}:{password}@{server}:5432/prisma_shadow"
```

As with the reset procedure, please revert the state to the point immediately before merging the migration folders.

```console
prisma/migrations/
├── 20261005000000_baseline
│   └── migration.sql
├── 20261005072036_add_created # ← remove
│   └── migration.sql
├── 20261005072437_add_updated # ← remove
│   └── migration.sql
└── migration_lock.toml
```

To create a new migration without resetting the database, run the following command.

```bash
# create directory
mkdir -p prisma/migrations/20261005990000_v1.1.0

pnpm prisma migrate diff \
  --from-migrations ./prisma/migrations/ \
  --to-schema ./prisma/schema.prisma  \
  --script > prisma/migrations/20261005990000_v1.1.0/migration.sql
```

At this stage, only the migration file is created.

Mark this migration as having been applied on production, to prevent it from being run there:

```bash
pnpm prisma migrate resolve --applied 20261005990000_v1.1.0
```

You are now ready to apply the next migration.

```console
$ pnpm prisma migrate deploy

Loaded Prisma config from prisma7.config.ts.

Prisma schema loaded from prisma/schema.prisma.
Datasource "db": PostgreSQL database "prisma", schema "public" at "postgres:5432"

3 migrations found in prisma/migrations

No pending migrations to apply.
```
